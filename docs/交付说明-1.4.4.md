# 交付说明 — RLL 1.4.4

## 一句话

修复「启动游戏后启动器卡死、游戏窗口很久才出来」——这是 1.4.3 引入的高频日志处理的副作用。

## 根因：不是游戏慢，是管道反压

游戏启动后会向 stdout/stderr 输出大量日志（Minecraft 首次启动常见几万到十几万行）。
这些行由 .NET 的异步管道读取器回调过来。旧实现对**每一行**都做了两件事：

1. `Log.Info(...)` → `File.AppendAllText(...)`——**每行都打开文件、写、关闭**；
2. 触发 `Log.Message` 事件 → 界面层对**每一行** `BeginInvoke` 一次。

关键在第 1 点执行在**管道的读取线程**上：

```
游戏 --写--> stdout 管道（缓冲区 4KB） --读--> 启动器的读取线程
                                                      |
                                                      +--> 每行同步 open/write/close 文件
```

管道缓冲区满了，游戏就必须等读取方把数据取走。读取方每行做一次同步文件 I/O，
取数据的速度跟不上游戏写的速度，**游戏就被卡在写日志上**——窗口迟迟不出来。

第 2 点则让 UI 线程被每行的 `BeginInvoke` 淹没，表现为"启动器未响应"。

> 「其它应用不受影响」恰好印证了这一点：瓶颈在启动器自己的管道读取路径上，
> 不是系统整体资源不足。

## 实测数据

同一个假游戏 exe（输出 8 万行），两种实现对比：

| 实现 | 游戏输出全部内容所花时间 |
| --- | --- |
| 旧（每行同步 open/write/close） | **16.16 秒** |
| 新（后台批量写） | **0.24 秒** |

**约 67 倍差距。**（用启动器真实的 `GameLauncher.Start` → `WriteGameLog` → `Log.Game` 链路测得）

## 修复

### 1. `Log` 改为后台写盘线程 + 批量写

- 行先进内存队列，后台线程每 200ms（或累计 200 行时）**一次性** flush 进文件；
- 管道读取线程几乎不做 I/O → **反压消失**；
- 退出时 `Log.Shutdown()` 把剩余内容落盘，不丢行。

### 2. 新增 `Log.Game` 高频入口 + `Log.GameMessage` 独立通道

- `Log.Game(...)` 只入队、不做同步 I/O；
- 游戏日志与操作记录**分开**，游戏日志不会再把用户的操作记录刷走；
- 界面层按批（最多 500 行一次）刷新到日志框，不再每行 `BeginInvoke`。

### 3. 顺带修掉两个隐藏问题

- `AppendLogText` 保留了 `InvokeRequired` 切回 UI 线程的逻辑
  （`Log.Info` 确实会从下载、依赖解析等**后台线程**调用，漏掉会跨线程改控件）；
- 批量刷新用 `Interlocked.CompareExchange` 做原子的"只安排一次"判定——
  stdout 与 stderr 是**两个不同的读取线程**，可能同时触发刷新。

## 验证

| 项目 | 结果 |
| --- | --- |
| 真实启动器链路（8 万行） | 16.16 s → **0.24 s** |
| 日志完整性 | 8 万行 **零丢失**（逐行核对文件内容与行号） |
| 离线单元测试 | **702 项通过，0 失败**（新增 4 项断言） |
| 界面冒烟测试 | **190 项通过，0 失败** |

新增回归测试：
- 「Log game channel is non blocking」——断言写 3 万行游戏日志的**入队耗时 < 3 秒**。
  如果有人把 `Log.Game` 改回同步文件 I/O，这条测试会立刻失败。
- 「Log content completeness」——断言 5000 行**全部落盘且顺序正确**。

## 升级注意

- 配置完全向后兼容，无需迁移。
- 日志内容与之前一致（只是写入方式变了），格式不变。
- 老版本留下的日志文件不受影响。

## 顺带说明

这个问题是 1.4.3 引入"游戏日志批量刷新"时埋下的：1.4.2 之前游戏日志走的是
`Log.Info`，同样是每行一次文件 I/O，但因为 1.4.2 之前没有专门的崩溃自动分析
与高速日志通道，用户在模组少的时候感知不明显；1.4.3 之后日志量更大，问题暴露。

**教训**：凡是跑在**管道读取线程**上的代码，都不能做同步阻塞 I/O——
这是 Windows 进程间通信的经典陷阱。
