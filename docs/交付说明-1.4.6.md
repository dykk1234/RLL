# 交付说明 — RLL 1.4.6

## 一句话

修掉两个「长期使用会出问题」的问题：日志撑爆磁盘、下载被误杀。

---

## 一、日志无上限增长（可能撑爆磁盘）

### 实测数据

```
launcher-20261101.log   351.7 MB   ->  42.3 MB/小时
采样 30 万行：游戏日志 299801 行，操作日志 199 行  ->  99.9% 是游戏输出
```

按 42 MB/小时推算，**30 天约 30 GB**，而 `Log.cs` 此前**没有任何保留策略**。

### 讽刺的是，这是 1.4.4 的性能修复放大的

1.4.4 的批量写修好了「游戏卡在写 stdout 上」，却让写入吞吐大幅提升，
日志涨得也快了。以前很多游戏日志**根本没落盘**——那正是当时卡顿的代价。

### 修复：三道闸

**① 单文件体积上限 + 轮转**
超过 64 MB 就轮转成 `xxx.1.log`、`xxx.2.log`…，最多保留 3 份，超出的丢弃。
界面日志框里仍然看得到——用户当场看得到，不必依赖文件。

**② 保留期清理**
启动时删除 30 天前的旧日志。只删 `launcher-*.log` / `game-*.log` 自己产生的文件，
不碰目录里的其它东西；**当前正在写的文件永远不动**。

**③ 游戏日志与操作日志分开归档**

```
logs/launcher-20261101.log   操作记录（启动器自己的日志）
logs/game-20261101.log       游戏 stdout/stderr
```

两者量级差 **3 个数量级**，可以分别制定保留策略。
更重要的是：**用户反馈问题时贴操作日志就够了**，不必贴几十 MB 的游戏日志——
这顺带降低了「用户整份贴日志求助」导致密钥外泄的风险面。

## 二、下载被固定总时长超时误杀（慢网络下必然失败）

### 根因

`HttpClient.Timeout` 覆盖的是**整个操作**（含响应体读取），不只是「等响应头」。
元数据请求用的是「每次尝试 60 秒」的独立超时，
**大文件下载却沿用了这个 15 分钟的全局超时**：

| 速度 | 50 MB | 200 MB | 500 MB |
| --- | --- | --- | --- |
| 0.6 MB/s | 1.4 分 ok | 5.6 分 ok | 13.9 分 ok |
| 0.2 MB/s | 4.2 分 ok | **16.7 分 FAIL** | **41.7 分 FAIL** |
| 0.05 MB/s | **16.7 分 FAIL** | **66.7 分 FAIL** | **166.7 分 FAIL** |

也就是说：**网络只是慢，下载却被中途掐断**，用户看到「下载失败」，
而实际连接是通的。重试又从 0 开始——**死循环**。

### 根本问题：固定总时长无法区分「慢」和「死」

一个 47 MB 的文件在 0.05 MB/s 的网络下需要 15 分钟以上，
但它**一直在动**，没有理由中断它。

### 修复：改用停滞检测（watchdog）

只有**连续 45 秒没有收到任何字节**才判定为卡死并中止：

- 慢但持续有数据的连接**不会被误杀**；
- 真正卡死的连接（服务器不响应、连接半开）在 45 秒内被及时发现；
- 卡死时给出可读提示：「下载停滞：xxx 已连续 45 秒没有收到任何数据，已中止」，
  而不是笼统的「已取消」。

### 实测验证（本地服务器）

| 场景 | 结果 |
| --- | --- |
| 每 250ms 传 4KB 的慢连接，**2 秒**停滞阈值 | **存活**，完整收到 40960 字节 |
| 完全无数据的连接 | **3 秒内被中止** |

第一行特别关键：停滞阈值只设 2 秒，慢连接依然活着——
证明判定依据是「有没有在动」而不是「总共花了多久」。

## 四、升级注意

- 配置完全向后兼容，无需迁移。

## 五、下一步

按分析报告的剩余优先级：

1. **版本清单 ETag 缓存**（每次刷新重下 1–2 MB）
2. **下载断点续传（HTTP Range）** —— 断网重来仍是痛点，
   与本次的停滞检测是互补的：停滞检测解决「卡死」，
   断点续传解决「断网后不用从头来」
3. **模组 id 索引（`ModIndex`）** → 批量更新、依赖检查的共同地基
4. **拆分 `MainForm.cs`**（已 6200+ 行）
