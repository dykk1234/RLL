# 交付说明 — RLL 1.4.7

## 一句话

修复「Java 下载进度永远显示 0/55MB」，并实现 HTTP Range 断点续传。

---

## 一、Java 下载进度一直显示（0/55MB）

### 根因：回调契约不一致

`HttpUtil` 的 `onBytes` 回调在不同位置分别传「增量」和「累计」：

```csharp
// 下载循环里：传的是增量（每次 80KB）
onBytes(read);

// 已存在文件的分支：传的是累计
onBytes(new FileInfo(targetPath).Length);
```

而 Java 下载的界面按**累计**解读：

```csharp
int percent = (int)(received * 100L / download.Size);
SetStatus("正在下载 Java：" + (received / 1024 / 1024) + " / " + ...);
```

于是每次收到的都是 80KB，整数除法后永远显示 **0 MB** —— 用户看到的就是
「下载一直显示 0/55MB」，完全看不出进度在动。

### 修复

1. **统一契约**：`onBytes` 一律传**累计**已下载字节数（下载循环改成 `onBytes(total)`），
   并在方法注释里写明契约。
2. **更新调用方**：`MinecraftInstaller` 原用 `Interlocked.Add`（增量语义），
   改为 `Interlocked.Exchange`（直接用累计值）。
3. **显示一位小数**：即使只有几十 KB 也显示 `0.1 MB` 而不是 `0 MB`，
   用户能看出进度确实在动。

> 这个问题靠肉眼看代码很难发现——两处都「看起来对」。
> 是用户实际反馈才暴露出来的，所以新增了契约测试锁住它。

## 二、断点续传（HTTP Range）

### 痛点

原版资源几百 MB 到 2GB。断网后重试**从 0 开始** —— 这是最难受的。

### 实现

- 下载中的文件写成 `目标名.<guid>.part`；
- 中断后保留分片，重试时发 `Range: bytes=N-` 请求续传；
- 服务端返回 **206 Partial Content** 即续传成功；
- 服务端**忽略 Range 返回 200** 时，自动丢弃分片从头下
  （**不会拼出损坏文件**——这是最容易写错的地方）；
- 分片只在 **SHA1 校验通过**后才被采用，无哈希校验的下载不启用续传；
- 下载成功后清理残留分片。

### 实测验证（真实 Mojang 服务器）

```
=== A. Resume from a partial file ===
created partial file with 139227 bytes
final file size = 278455
sha1 matches = True
onBytes last value = 278455 (expected 278455)
RESUME OK = True

=== B. Fresh download: onBytes must be CUMULATIVE ===
calls = 11 max = 278455 last = 278455
CUMULATIVE OK = True
```

即：**从 139KB 的分片继续，只取回剩余部分，最终 SHA1 与完整下载一致。**

服务端支持情况实测（真实 Mojang 清单）：

```
from=0     status=200 contentRange=(none)                    len=278455
from=1000  status=206 contentRange=bytes 1000-278454/278455   len=277455
```

### 安全边界不变

续传只是**同一白名单内同一资源**的字节范围请求：

- 不新增域名；
- 不放宽校验；
- 最终仍要通过**完整的 SHA1 校验**才写入目标文件；
- 分片文件只落在目标文件同目录，命名规则固定，不会被路径穿越利用。
